# Kaspi Pay: подключение оплаты SANAQ

## Что реализовано

В SANAQ есть три MVP-тарифа по 1 ₸, серверный реестр платежей и подписка на 30 дней.
Frontend никогда не активирует доступ самостоятельно: состояние `paid` может установить
только backend — администратор после сверки либо отдельный подтверждённый provider callback,
когда Kaspi предоставит его конкретному merchant.

Открытая схема Kaspi Pay «Ссылка для оплаты» работает так: партнёр получает ссылку для
конкретной точки продаж, размещает её на сайте, а покупатель после перехода сам вводит сумму
и сообщение. Поэтому текущий production-адаптер использует реальную merchant-ссылку и
ручную сверку. Он не выдаёт возврат со страницы за успешную оплату.

## 1. Получить merchant-ссылку

1. Организация должна быть подключена к Kaspi Pay.
2. В мобильном приложении Kaspi Pay откройте `Kaspi Pay → Удалённая оплата → Ссылка для оплаты`.
3. Скопируйте ссылку точки продаж. Не придумывайте адрес и не используйте ссылку другого
   магазина.
4. Выполните тестовый платёж и проверьте поступление в Kaspi Pay до показа судьям.

Официальная инструкция: <https://guide.kaspi.kz/partner/ru/pos/payments/remote/q2019>.

## 2. Настроить backend на хосте

Добавьте только на сервере в `backend/.env`:

```dotenv
PAYMENT_PROVIDER=kaspi
KASPI_PAYMENT_MODE=kaspi_link
KASPI_PAYMENT_URL=https://pay.kaspi.kz/pay/ВАША_ССЫЛКА
KASPI_ALLOW_DEMO_CHECKOUT=false
```

Затем создайте новые таблицы и перезапустите контейнер:

```bash
docker compose run --rm backend flask --app app init-db
docker compose up -d --build backend
```

`KASPI_PAYMENT_URL` не является секретом — это публичная ссылка точки. Но изменять её на
production должен только администратор хоста.

## 3. Как проходит платёж

1. Ученик выбирает тариф на `/student/billing`.
2. Backend создаёт `Payment` со случайным `SANAQ-...` reference и суммой 100 тиын.
3. Интерфейс показывает ровно `1 ₸` и reference.
4. Красная кнопка открывает настоящую merchant-ссылку Kaspi Pay в новой вкладке.
5. Покупатель вводит `1 ₸`, добавляет reference в сообщение и подтверждает платёж.
6. Администратор открывает `/admin/billing`, сверяет сумму/reference с Kaspi Pay и нажимает
   «Подтвердить».
7. Backend атомарно меняет платёж на `paid` и активирует/продлевает подписку на 30 дней.

Повторный POST защищён `Idempotency-Key`: двойной клик не создаёт вторую попытку с тем же
ключом. Пользователь не может посмотреть чужой платёж. Оплаченную запись нельзя отменить.

## 4. Локальный demo-режим

Для разработки:

```dotenv
KASPI_PAYMENT_MODE=demo
KASPI_ALLOW_DEMO_CHECKOUT=true
KASPI_PAYMENT_URL=
```

Demo checkout визуально и текстом обозначен как симулятор SANAQ. Он не использует имя,
домен или интерфейс Kaspi и не списывает деньги. В production пример конфигурации запрещает
его по умолчанию.

## 5. Когда Kaspi выдаст API или callback

Не добавляйте выдуманный webhook и не подтверждайте оплату по query-параметру `success`.
Получив официальную техническую спецификацию именно для вашего договора:

1. добавьте отдельный provider adapter;
2. проверяйте подпись/сертификат и allowlist по спецификации Kaspi;
3. сопоставляйте provider transaction ID с `provider_reference`;
4. обрабатывайте callback идемпотентно;
5. вызывайте `activate_payment()` только после серверной проверки статуса;
6. храните raw payload только без лишних персональных данных и никогда не логируйте ключи.

До этого момента ручная сверка — намеренное ограничение безопасности, а не ошибка.
